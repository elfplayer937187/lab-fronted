# 接口通用约定

本文只讲**所有接口都一样的部分**（响应外壳、状态码、命名、请求头）。
每个接口各自的业务字段见接口文档本身，这里不重复。
后端地址 http://localhost:8000/docs#
---

## 1. 统一响应结构

所有接口，无论成功还是失败，返回体都是同一个外壳，**固定三个字段，不多不少**：

```json
{
  "code": 200,
  "message": "修改成功",
  "data": null
}
```

| 字段      | 类型               | 说明                                            |
| --------- | ------------------ | ----------------------------------------------- |
| `code`    | `int`              | 业务码，判断成功失败的**唯一依据**，见下表      |
| `message` | `string \| null`   | 提示文案，可直接拿去 toast；成功时可能为 `null` |
| `data`    | 任意类型 \| `null` | 业务数据，形态随接口而定；没有返回体时是 `null` |

`data` 内部的字段**每个接口各不相同**，不在这里列。

---

## 2. HTTP 状态码和业务码是两套东西

这是最容易踩的坑，重点看：

- **HTTP 状态码**：给网关、日志、浏览器网络层看的，不要用来判断业务。
- **`body.code`**：给前端判断分支用的，**只认它**。

判断请求是否成功，写这个：

```js
if (res.data.code === 200) {
  /* 成功 */
} else {
  /* 失败，拿 res.data.message 提示 */
}
```

**不要**用 `res.ok`、`res.status`、也不要用 axios 拦截器的 HTTP 状态来判断业务成功。

为什么会分叉：同一个业务码在不同接口的 HTTP 语义可能不同。例如「用户不存在」在登录接口回 `401`（登录失败），在查询用户详情时回 `404`。所以前端如果依赖 HTTP 状态码，同一个业务错误在不同接口会走上不同的分支 —— 这正是要避免的。

---

## 3. 业务码 `code` 取值表

| code  | 含义                      | 前端建议处理                        |
| ----- | ------------------------- | ----------------------------------- |
| `200` | 成功                      | 正常走业务                          |
| `400` | 参数错误                  | 看 `data` 里的详情数组（见第 4 节） |
| `401` | 未认证 / token 无效、过期 | 清 token，跳登录                    |
| `403` | 无权限 / 账号被禁用       | 提示，不跳登录                      |
| `500` | 系统错误                  | 通用错误提示                        |
| `201` | token 无效                | 同 `401`，清 token 跳登录           |
| `202` | token 访问被拒绝          | 同上                                |
| `203` | 访问未授权                | 同上                                |
| `230` | 账号已存在                | 提示用户换账号                      |
| `231` | 用户不存在                | 按接口语义提示                      |
| `232` | 用户被禁用                | 提示，不跳登录                      |
| `240` | 未知错误                  | 通用错误提示                        |

**前端只需要认真区分两类**：`200` 走成功；`401/201/202/203` 统一当作「登录态失效」处理；其余按普通错误弹 `message`。

---

## 4. `data` 的几种常见形态

`data` 是 `null` 还是对象，取决于接口有没有返回体。但有一种形态是**固定的**：

**参数错误（`code: 400`）时，`data` 一定是一个字符串数组**，每一项形如 `"body.username: Field required"`：

```json
{
  "code": 400,
  "message": "参数错误",
  "data": [
    "body.username: Field required",
    "body.phone: String should match pattern '^1[3-9]\\d{9}$|^$'"
  ]
}
```

前端可以直接 `map` 成表单的字段错误提示，不解析也能整体展示。

其余情况：

- 成功但无返回体（如修改资料）→ `data: null`
- 成功有返回体 → 对象或数组，字段名见各接口文档
- 其他错误 → 通常 `data: null`

---

## 5. 命名约定

**响应外壳字段名固定**：`code` / `message` / `data`，所有接口一致，全小写。

**鉴权头是标准的 `Authorization: Bearer <token>`**：

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

后端不认单独一个 `token:` 头，那样发过去会回 `code: 201`「未找到token」。

**请求体字段名**：后端对未声明的字段是拒绝的（`extra='forbid'`）。前端**多传一个字段就会收到 `400` 参数错误**，而不是被后端忽略。所以请求体严格按接口文档给字段，不要顺手带上表单里的其他值（尤其是 `role`、`status` 这类，传了必然报错）。

> 时间字段、分页字段目前接口还没返回过，等出现了再补进本文档，不要按惯例猜。

---

## 6. 写请求时的一个小约定

更新类接口的字段都是可选的，只传要改的那几项。

**清空一个字段要传空字符串 `""`，不能传 `null`**：显式传 `null` 的字段会被后端当作「不修改」，而且像 `name` 这种非空字段传 `null` 会直接报 `400`。

```json
// 想清空手机号 ✅
{ "phone": "" }

// 传 null 无效，不会清空 ❌
{ "phone": null }
```

同理，更新接口至少要传一个字段，传空对象 `{}` 会收到 `400`。

---

## 7. 本地联调用的测试账号

后端 dev 库里有个现成的临时账号，验证接口字段时直接登录拿 token，不用每次重新注册：

```json
POST /api/auth/login
{ "username": "claude_probe", "password": "claude123456" }
```

返回的 `data.token` 配上 `Authorization: Bearer <token>` 就能调受保护的接口。账号的用户 id 是 8，要重建就先 `DELETE /api/user/delete?userId=8`。

> 只是本地 dev 的临时账号，别用到线上。
